## 🐛 BUG confirmado e CORRIGIDO — regras duras C1 estavam mortas
Em `src/app/api/os/route.ts:44-46`, as flags imobilizada/acidente/guincho eram lidas com
`JSONExtractBool(maintenance_metadata, 'checklist_tags.immobilizing')` (caminho pontilhado).
O ClickHouse **não** navega JSON aninhado com ponto → retornava **0 para 100% das OS** (8181/8181).
Prova: pontilhado = 0/0/0; sintaxe correta (args separados) = **55/14/197** em 30d.
**Efeito:** moto imobilizada/acidentada/guincho NÃO disparava reserva imediata por C1.
**Fix aplicado:** `JSONExtractBool(meta, 'checklist_tags', 'immobilizing')` (idem accident/towing).
Ressalva: mesmo corrigido, `checklist_tags` só existe em ~10% das OS de piso → C1 hard cobre <0,5%
do piso. Quem realmente segura o piso é **C3**.

## 3. Peça sem estoque (Camada 2) — funciona, mas tem 3 furos
**Como é hoje:** pra cada peça do diag, soma estoque AVAILABLE em depósitos STORAGE+STAGING **na mesma base**;
se disponível < necessário → C2 (reserva), antes de C3. Estoque fresco (lag ~2 min). **~6,6 OS de piso/dia** disparam.
Furos:
1. **NULL→0:** peça sem nenhuma linha de estoque na base vira 0 e dispara (22 de 207 pares = **11%**). Mistura
   "falta de dado" com "falta real" — logar separado.
2. **Ignora depósitos MAINTENANCE (2778 un, peça na rampa) e PERSON (214):** peça na bancada pode gerar reserva indevida.
3. **Cross-base:** só olha a base da OS. Baú 93L: Mooca=0 / Osasco=162 / SBC=4 → Mooca dispara mesmo com 162 em Osasco.

**Surpresa:** as campeãs de falta são **ACESSÓRIOS** (Baú 93L, USB 18W, Chapa do baú, Peso do guidão) — **NÃO** disco
dianteiro (o exemplo do doc está desatualizado; disco/pinça/pastilha estão bem abastecidos). C2 trata acessório com o
mesmo peso de peça crítica → possível excesso de reserva. (Guarda `qty_disponivel>0` do SQL é inerte: 0 casos
positivo-mas-insuficiente.)
